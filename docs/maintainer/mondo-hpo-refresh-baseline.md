# Proposed MONDO/HPO refresh baseline

The current loader refuses a disease-scope match rate below 40%. This proposal for #2500 adds a comparison with the installed release and a check for complete loss of a previously matched namespace. The choice affects which reference refreshes an operator can install. This page records the evidence for that decision. [Issue #2707](https://github.com/bioedca/Yeliztli/issues/2707)

## What the releases showed

Fourteen dated public release triplets produced intact match rates of **58.80% to 87.81%**. Across all 36 earlier-to-later combinations of the first nine releases, the largest intact drop was **12.6506 percentage points**, from September to November 2025. Choosing the smallest whole number strictly above that maximum gives **13 points**. This rule preserves every measured calibration transition, including skipped releases. It offers only 0.3494 points of margin on the worst observed transition.

We then compared each of the five later intact releases or its damaged counterpart to every earlier intact installation. The table shows how often a candidate was refused in these 55 comparisons. The last column adds a refusal if any namespace contributing at least one installed match contributes zero candidate matches. All three rules retain the current absolute floor.

| Candidate | 40% floor | Add 13-point drop | Also check namespace loss |
| --- | ---: | ---: | ---: |
| Intact | 0/55 | 0/55 | 0/55 |
| Remove OMIM mappings | 55/55 | 55/55 | 55/55 |
| Remove Orphanet mappings | 0/55 | 5/55 | 55/55 |
| Keep about half of Orphanet mappings | 0/55 | 0/55 | 0/55 |
| Keep about 75% of all mappings | 0/55 | 38/55 | 38/55 |
| Keep about 90% of all mappings | 0/55 | 4/55 | 4/55 |

For just the five **adjacent** held-out upgrades, the 13-point check caught **zero of five** complete Orphanet losses. Adding the namespace check caught five of five. Of the same five candidates retaining about 75% of mappings, both combined rules caught four. November 2026's intact rate rose from 64.82% to 87.81%. Its 75%-retention candidate still matched 64.65%, close to October's intact rate. An improving source can conceal substantial damage. A competent release that retires or renames a whole namespace could also trigger the proposed guard. Repeated smaller losses across successive accepted installations can accumulate. A namespace cutoff for *partial* loss needs separate calibration.

The experiment covers the scope-rate gates. Other loader guards, including the minimum mapping count, run independently in production. Source releases share data, and this sample offers five holdout dates. The intact designation means unmodified upstream files. Semantic coverage and clinical accuracy require other evidence. The [evidence packet](https://github.com/bioedca/Yeliztli/tree/main/data/science-evidence/2026-11-19-mondo-hpo-refresh-2707) contains the source register, scripts, five overlapping replications of #2285, 84 measured cases and all comparator results.

## Proposed decision

Retain the 40% floor and refuse a decline **greater than 13 percentage points** versus the committed predecessor. Include the complete-namespace check for previously positive matches. Store per-namespace matched and unmatched counts so an operator can see what changed. Show the old and new counts, bundle identities and reason on refusal. The first install or a verified legacy installation uses only the absolute floor among these three checks.

For matched counts `a` and `b` in positive totals `A` (installed) and `B` (candidate), the relative check refuses when `100 * (a*B - b*A) > 13*A*B`. Use exact integers. Exactly 13 points passes. The absolute check refuses when `100*b < 40*B`, so exactly 40% passes its own gate. A zero denominator or malformed count fails validation. Decide each gate separately, including on equal rates.

## Atomic storage and recovery

Use the **reference SQLite database** already holding `gene_phenotype` and `database_versions`. Add a proposed source-specific baseline table with a unique installation key (the three-file bundle identity plus measurement-format revision), nonnegative integer totals and per-namespace counts with the same installation key. Retain all three input digests, the current composite installer version and measurement-format revision. Use the loader's existing `_source_bundle_id(sources)` and `_mondo_hpo_install_version`. The primary KG checksum alone cannot distinguish two installations that differ only in HPO or MONDO. `reference_metadata` names a SQLAlchemy metadata collection in this repository.

Record the active baseline key, a verified seed-only state, or an explicit migration-issued legacy state in a new MONDO/HPO-only installation-state table. Bind it to the entire existing installation tuple in the same transaction. The source, composite version and primary checksum must agree, and the bundle named by `database_versions.file_path` must have the recorded bundle ID. Use the existing descriptor-anchored managed-bundle validation to obtain the committed manifest, verify its digest and role-ordered source identities and recompute `_source_bundle_id`. Store the expected manifest SHA-256 in the source-specific state transaction using `_published_source_manifest_sha256` on the **published** bundle. On a source-identical retry this selects the original retained manifest, whose retrieval timestamp can differ from the staged one. Match the manifest digest, three input digests and ingestion revision against the baseline. Identical secondary HTTP validators, or missing validators represented as unknown, do not identify content. On a normal refresh or identical retry, refuse mismatched paths or unavailable managed-bundle identity with no network fallback. Keep the existing columns and serialized field set of `database_versions` intact. The schema-1 standalone publication journal checks every version-row field before migrations run. Exercise startup with an actual pre-upgrade journal and matching standalone file, then verify replay and the recovered version. A seed-only state carries its seed source digest and row fingerprint. Give its source version an explicit nonserviceable seed stamp that fails the existing current-ingestion predicate. Only a verified bundle install may replace it with a serviceable stamp. It can be created only by an explicit seed install into an empty store. Backfill the legacy state only for an existing installation the migration positively identifies. Fresh schema initializes empty. Validate installed version, rows, key, counts, namespace sums, format and bundle identity together. A missing required table on a migrated database, mismatched pointer, unexpected orphan row, unknown revision, unreadable database or malformed counts refuses the operation. A missing baseline row behind an active key means corruption. Restore from a verified backup or use a separately verified rebuild of the same pinned inputs. A corrupt installation must never be downgraded to legacy by deleting its baseline.

Bind the active baseline to both its inputs and the actual installed rows. Store a count and SHA-256 over **all** persisted `source = 'mondo_hpo'` rows. A versioned canonical encoding uses the six stored data columns (gene symbol, disease name, disease ID, HPO terms text, source, inheritance) in a fixed order. Encode each tuple as a compact UTF-8 JSON array with explicit nulls, sort encoded tuples by raw bytes and hash each length-prefixed tuple, including duplicates. Define the prefix as an unsigned 64-bit big-endian byte length. Exclude the generated row ID. After writing the candidate, read back and fingerprint the durable row values on the publishing connection before commit. Verify the installed fingerprint under the write reservation before comparing the baseline or accepting an identical retry. A modified or missing row refuses even if both namespace sums still agree. Input-scope counts cannot be reconstructed from the projected rows. Bind them independently: store a SHA-256 of the canonical measurement record in the separate active installation pointer. Encode one fixed-order JSON array containing measurement revision, bundle ID, matched and unmatched totals, then the namespace/name/matched/unmatched tuples sorted by namespace. Use compact UTF-8 JSON, no optional fields or duplicate namespaces, and nonnegative integers. Before comparison, reconstruct this payload from the baseline records and compare it with the digest on the pointer. The binding detects inconsistent partial restoration; restoration of an entire database from a different point in time must follow the normal verified-backup procedure.

Before generic table creation, inspect the actual SQLite schema under the existing `BEGIN IMMEDIATE` in `bootstrap_reference_schema_tables`. Use a reference-database schema revision in the file's `PRAGMA user_version` header as an independent migration witness. The existing uses in `sample_schema.py` apply to separate sample files. Reserve revision 1 for this first use in the reference database, subject to verifying supported legacy fixtures have revision 0. Unknown nonzero values require explicit compatibility review and must never be overwritten. A current header requires the entire expected schema, even when the installation is empty or legacy. Partial new objects with an old header, missing objects with a current header or an unknown layout refuse. Initialize an empty store or the known initial logging-only layout, or migrate a recognized old layout with no new objects, in one transaction. On first FastAPI startup, `ensure_log_entry_presentation_policy` may already have created the production `log_entries` table and its indexes. Recognize that exact logging-only schema (including SQLite internal objects) at header 0, preserve its records, and initialize the remaining schema. A current header with only a log table is corrupt. Exercise both initializers in their real orders, including Huey starting before FastAPI. Record source states, create the tables and set the header together. Run the same schema precheck as the first operation, under reservation, in both bootstrap and `ensure_log_entry_presentation_policy`. The latter runs first on the FastAPI path and could otherwise recreate a missing `log_entries` table on a migrated database. Under a current header, validate required tables, columns and indexes before the logging helper applies any repair. Preserve its ordinary policy backfill on a recognized old schema. Direct Huey startup follows the same precheck before DDL. Direct managed refreshes also validate the schema before writing.

### Partial installations and explicit recovery

The older `clean_database_artifacts` operation deletes the version and leaves MONDO/HPO rows in the shared database. A legacy seed can also have rows without a version. The one-time migration records those indistinguishable states as **unverified legacy rows**, with a recovery marker and a deterministic fingerprint of the source rows. It does not infer who cleaned or seeded them. After migration, both ordinary refresh and ordinary clean must refuse that marker before touching any row, metadata or source artifact, even when health reports `partial`.

Expose a distinct recoverable state in the database-health response. It suppresses ordinary Clean/Retry for a migration-marked installation. Setup must offer **Rebuild verified MONDO/HPO data**, send a source-specific explicit recovery request, and display the returned job's progress and result. Implement a dedicated recovery action for this database that can dispatch the existing build job with recovery intent only after checking the live marker. Keep ordinary build, automatic refresh and clean on their usual paths. If the marker changes between enqueue and execution, the worker refuses. Test through the rendered setup control and job, including failure, retry and an unrelated database whose available actions stay the same.

For an explicit source rebuild:

1. Download, stage, verify and measure the candidate, including the absolute floor, **before reserving the database write**. This keeps downloads and setup progress updates outside the shared database transaction.
2. Under the database and bundle claims, acquire `BEGIN IMMEDIATE`, then re-read the marker and fingerprint on the reserved connection. A mismatch aborts. Replace only the verified old MONDO/HPO rows and consume the marker in the transaction that publishes the new rows, baseline and version. Failure retains both rows and marker for retry.
3. A post-migration installation cannot acquire this one-time recovery marker. Generic clean must refuse a live marker or inconsistent active baseline. For another installation that passes the existing cleanup-health criteria, the upgraded clean path rechecks health and starting identity under the write reservation, then clears only its MONDO/HPO rows, baseline, active pointer and version together. Reconcile source artifacts through the existing pending-bundle protocol. Complete cleanup leaves a genuinely empty first-install state. The health probe must test for at least one `gene_phenotype` row with `source = 'mondo_hpo'`. Independent OMIM rows can keep the shared table nonempty. With no MONDO/HPO rows or version, the normal clean/rebuild flow reports this source absent when there is no separate failed/active job. It must not offer Clean just because OMIM has data.

### Managed publication

1. Parse and measure the candidate from the already staged inputs. Bind measurements to their verified hashes. Under the existing database and bundle claims, compare the starting installation with the current one. Under the process-local serialized writer, execute `BEGIN IMMEDIATE` on the reference SQLite connection **before the first predecessor read**, following the existing reference-schema migration pattern. Re-read the installation and baseline under that reservation. Compare them with the starting installation, then read, replace and commit on the same connection. A competing cleaner or writer must wait or return busy. After acquiring the write, it must recheck its own starting state. Python 3.12 legacy SQLite transaction control can leave a plain SELECT inside a SQLAlchemy transaction outside the database transaction until the first write. Refuse stale or damaged candidates before deleting any installed row. A refresh comparison requires no additional network lookup.
2. Capture the absolute-floor fallback reason in memory when the store is empty, the migration marked a consistent legacy predecessor, or an explicit first bundle upgrade verifies the seed-only digest and row fingerprint. Treat ambiguous states as errors. On success insert the new rows, installed version, baseline counts and active pointer together. Every path that can mutate the source rows, version, pointer or baseline must preserve this invariant or refuse **before the first write**. This includes the row-only CSV loader, `load_mondo_hpo_rows(version=None)`, append mode and `record_mondo_hpo_version` even if the version text would be identical. A CSV supplies no three-file match counts. Validate every input source label before opening a write. The MONDO/HPO seed may create only `source = mondo_hpo` rows. Reject a mixed or foreign label as a whole batch. Only the independent OMIM loader owns OMIM rows. A supported standalone seed on an empty store requires an explicit seed-only identity and fingerprint committed atomically with its rows, followed by the first verified bundle install using the absolute floor. On an active installation refuse a bare seed, append or stand-alone stamp. A legacy recovery marker permits only the explicit recovery path. Preserve access by other source writers to their own rows. Keep existing source-verification callbacks through the commit boundary.
3. On refusal, write failure or rollback, preserve the previous rows, version and baseline. Reuse the loader's existing reconciliation for a pending source bundle left by a crash. Reopen the database after an uncertain commit and read the durable pointer before retry. An identical retry may report the existing installation when identities, counts and rows agree. A contender that measured against a stale predecessor must restart its comparison against the newly committed installation.
4. Capture the decision, aggregate counts, namespaces and public source identities while validating. After the transaction commits or rolls back and the write reservation is released, emit the corresponding success, fallback or refusal event. The API and Huey logging processor writes to the same reference database on another connection. Keep logging and progress callbacks that can issue database writes outside the reservation. A failed installation must never emit a success event. A genuine upstream retirement or a new measurement definition needs separate review with pinned releases and an explicit migration or operator recovery procedure. A missing candidate namespace is zero for the disappearance check. On the installed side, a missing namespace record whose absence makes totals inconsistent is corruption.

For user-visible reads, a legacy version stamp alone cannot prove how its current rows were loaded. Migrate a serviceable legacy install only after replaying the immutable retained inputs with its identified ingestion algorithm and comparing the canonical resulting rows against the database. Capture version/bundle/rows first, do the potentially long local replay outside the write reservation, then reacquire it and verify the captured state before publishing the result. Withhold the affected source until verification completes. If replay is unavailable, the ingestion algorithm is unknown or the rows differ, record the unverified recovery state and offer the explicit rebuild. Its marker binds the original state including any retained version and bundle. It cannot be minted later to downgrade a corrupt active baseline. Even when replay proves the old rows, the first managed update logs legacy fallback and applies the absolute floor per #2500. Superseded ingestion revisions remain subject to the existing serviceability predicate. A seed-only or unverified recovery state withholds MONDO/HPO and keeps the independent OMIM stream available. A healthy verified current bundle serves rows and satisfies setup readiness. A corrupt state refuses the managed refresh and withholds the affected source while leaving unrelated sources available. ## Acceptance cases for #2500

Use the actual load and database write path with synthetic bundles. Verify exact rows, prior and new version, baseline key, digests and namespace counts after each attempt.

| Case | Expected outcome |
| --- | --- |
| Same, just under, exactly at and just over a 13-point drop | With all other gates passing, accept the first three and refuse the last before replacing rows. Include unequal denominators. |
| First install and real pre-migration install | Apply the floor, log the distinct fallback and publish an active keyed baseline with the rows. |
| Clean partial install before migration, then rebuild | Call the legacy production clean path. Confirm residual MONDO/HPO rows and missing version, migrate, attempt ordinary refresh and production clean, verify both preserve the marker and fingerprinted rows, then explicitly rebuild and reopen. Include a setup progress callback that writes through another connection during staging. Verify unrelated source rows survive and a failed rebuild is retryable. |
| Missing current baseline, incorrect digest, negative/zero total, inconsistent namespace sum, unreadable store | Refuse and preserve state. Exercise a missing migrated table separately from a positively marked legacy row. |
| Pre-upgrade standalone publication receipt at startup | Replay an existing schema-1 receipt before reference migration. Preserve the standalone data, version, receipt validation and all original metadata fields. |
| Modified/deleted active source row, unchanged counts and version | Refuse both a later candidate and an otherwise identical retry. Other-source rows and regenerated row IDs do not affect the digest. |
| Seed-only install and clean with independently served OMIM rows | Before the bundle, verify MONDO/HPO is withheld, OMIM is served and setup requires a build. After verified upgrade, both sources are served. The upgraded ready bundle refuses Clean with HTTP 409 and its state stays intact. In a separate fixture with an eligible partial install, clean through the production route and verify MONDO/HPO is absent, OMIM remains served and Clean is no longer offered. |
| Already migrated database loses a required table with an empty, legacy or active install | Reopen through API and worker startup. Both refuse before auto-creation. A recognized old schema and a truly fresh database still initialize. |
| API/worker logging with a file-backed reference database | Verify a first-install/legacy fallback is durably logged after commit. Refusal logs after rollback, preserves the installed data and emits no success event. |
| FastAPI and worker first startup | Start with a fresh data directory through the real lifespan and separate direct worker. Verify the logging-only initialization preserves log rows, repeated initialization succeeds, and a migrated database missing baseline tables still refuses. |
| Legacy stamp surviving versionless row replacement | Use the old versionless writer after a verified install, then migrate. Withhold changed rows, keep OMIM available and expose the explicit setup rebuild. For intact replayable data, preserve serviceability. |
| Migrated database missing the log table | Start the real FastAPI lifespan. Refuse before logging DDL can recreate it. Header-0 fresh/log-only startup still succeeds. |
| Internally consistent counts copied from another release | Change both totals and per-namespace counts while preserving their sums. Check the active pointer rejects the measurement digest mismatch. |
| Changed manifest timestamp and identical source refresh | Refuse tampered retained manifest bytes. A valid existing published bundle with a differing staged retrieval time retains its original digest. |
| Two same-version bundles with matching primary but different HPO or SSSOM contents | Point the recorded version at the alternate bundle. Publishing and identical retry must refuse even if the secondary validators and scope counts agree. |
| Mixed input labels in a source seed | Include a foreign OMIM row after valid MONDO/HPO rows. Refuse the entire operation before writing, confirm all prior source rows, and preserve genuinely independent OMIM rows. |
| Benchmark bootstrap and seed | Retain the complete assertions in `test_synthetic_gene_phenotypes_are_served` and the unstamped/legacy negative control. An interrupted fixture install must leave no partly served synthetic rows. |
| Namespace disappears with otherwise acceptable rate | Refuse. A previously unseen namespace and a still-positive namespace pass the disappearance check. |
| Floor at and just below 40%, or zero candidate total | Equal passes its floor, below refuses. Zero total refuses before comparisons. |
| Active installation followed by row-only CSV, versionless bulk replacement/append or stand-alone stamp | Call the real entry points. Each must preserve the atomically validated state or refuse before writing. Verify an explicit fresh seed can upgrade without invented match counts. |
| Failed insert, final precommit guard or process interruption | Reopen and observe an entirely old or entirely new installation. Verify pending bundle reconciliation and identical retry. |
| Concurrent refreshes from separate source directories against one database | One installation owns the write. A stale contender rechecks the committed predecessor or aborts. |
| Cleaner on an independent connection between predecessor read and row replacement | Use two file-backed connections. Confirm the reserved write fences the cleaner until commit or rollback and the cleaner rechecks health and installation identity. |
| Healthy upstream change or gradual partial loss | Surface counts and decision reason. Apply a reviewed change in policy when evidence warrants it. |
