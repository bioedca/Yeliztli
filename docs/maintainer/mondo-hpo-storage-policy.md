# Proposed MONDO/HPO directory and retention policy

For #2316, use one directory assessment at setup and at each MONDO/HPO build. Create app-owned directories privately, guide the operator to another location when the selected hierarchy is unsuitable, and put verified long-lived source bundles under persistent `data_dir`. Keep `download_staging_dir` available for disposable downloads. MONDO/HPO is required for setup, so a refusal needs a route back to storage selection and an actionable reason. This proposal awaits a decision in [#2711](https://github.com/bioedca/Yeliztli/issues/2711).

## Current behavior

At `7be123f382be44cc3c0936d2787038886b6488f7`, selecting storage with a separate private staging override succeeded. The setup route inspected the ancestry of `selected/downloads` and measured free space on the override. A separate miniature three-file build through `Settings.downloads_dir` recorded its primary source under `override/mondo_hpo_sources/<bundle-id>/`. Its HPO and mapping siblings were in the same directory. Both observations used temporary directories and synthetic inputs. The name and configuration description of the override invite operators to discard that volume, while the installed database records a path into it.

Setup currently creates missing path components with mode 0700 and clears group/other write bits on app-owned leaves. Foreign ownership and writable ancestors generally produce advisories. Independent access or structure errors can still prevent setup or a build. Some earlier source comments and test names describe former refusals. The current assertions and return values establish the baseline.

## One assessment, two points of use

The candidate settings determine three roles for directories holding persistent data, transient downloads and retained MONDO/HPO sources. Present the effective paths locally before saving the selection. Use the same ownership, permissions, ancestry and storage-capability rules in Setup, the initial reference install and the background update worker. Classify each result as usable, repaired, or requiring operator action. Include the role, local offending component, reason and remedy. Record a stable reason and role in durable diagnostics. A path chosen at setup may have changed when the worker starts, so re-evaluate it before writing and retain the existing descriptor, manifest, identity and durability checks during publication.

| Environment | Proposed result in both Setup and build | Operator or application action |
| --- | --- | --- |
| New destination under cooperative umask 0002 | Usable after creation | Create each new app directory at 0700. Verify the resulting attributes under the identity that will build the bundle. |
| Several missing parents | Usable after creation | Create and verify each missing component. Preserve existing parent permissions. On failure identify the first unsuccessful component. |
| Existing app-owned writable leaf, e.g. 0775 | Repaired if write bits can be cleared and verified | Clear only group/other write bits on that app-designated leaf. Preserve pre-existing read/traverse grants. On failure offer an app-owned alternative. |
| Restored or provisioned 0755 leaf owned by a different account | Readable existing evidence can be inspected. New writes require an app-owned working and publication leaf. | Have the administrator provision an app-owned child in a trusted hierarchy or select a directory owned by the running service. Preserve the original owner's directory. |
| Non-sticky group/world-writable ancestor, including a shared mount outside app control | Require another hierarchy for a new write. A 0700 child alone does not satisfy the ancestor rule. | Identify the component in the local dialog. Offer a persistent user directory or administrator-provisioned mount under suitably controlled ancestors. The former advisory behavior is an explicit alternative below. |
| Trusted system-owned ancestor or standard sticky temporary boundary | Usable when existing platform-boundary checks pass and the app-owned child meets its role | A disposable volume is eligible for staging. Persistent data and retained sources need a durable destination. macOS must retain its recognized system-boundary behavior. |
| Explicit `download_staging_dir`, on the same or a separate volume | Apply the staging predicate to the effective override and the durable predicate to the retained root | Name the setting when it fails. Changing only the selected data path cannot repair an independent override. Recheck free space for each role, combining simultaneous requirements on a shared filesystem. |
| Missing access, wrong object type, or inability to verify required ownership or publication durability | Require remediation before writing | Give the local path, role and specific failed requirement. Test the replacement with the same predicate. For a required setup do not persist a rejected path or mark the database ready. |

A foreign-owned ancestor can be suitable when it is an established trusted platform or administrator boundary and passes the existing ownership and permission checks. An arbitrary foreign owner needs explicit remediation. A mode of 0755 alone establishes neither ownership nor service write access. Do not recursively change permissions on a selected directory tree.

For example, the local dialog for an unusable staging override should say “The download staging folder at ‹folder› cannot be used by the reference-data worker. Select a private staging folder or update the download staging setting, then retry.” A retained-root error should name the persistent-data choice instead. Provide a reachable retry and preserve the prior effective settings and installed version on failure. An initial setup stays incomplete until a required install succeeds. A rejected refresh leaves the existing verified database usable.

## Retention, upgrades and interrupted work

Place new bundles in `data_dir/mondo_hpo_sources/<bundle-id>/`. Keep temporary inputs in the effective download directory. Each committed bundle includes the primary source, HPO source, mapping and manifest. Publish an immutable verified copy on the retained filesystem and durably synchronize it before committing the installed rows, version, checksum and file path. Across filesystems, first copy and verify into an app-owned temporary directory on the destination. Publish there only after it is complete. Reuse a previously published identical bundle after verification. Keep the existing database and publication claims and the pending-marker recovery from [#2614](https://github.com/bioedca/Yeliztli/issues/2614) and [#2615](https://github.com/bioedca/Yeliztli/issues/2615). The destination requires capacity for the incoming copy while the previous committed bundle remains available.

For existing installations, inspect the committed database version, primary path and checksum. Look for that exact content-addressed directory under the recorded eligible legacy root, including an explicit override. Verify its manifest and all three sources before copying. Under the normal publication claims, recheck that the installed identity is unchanged, verify the destination copy, and then update its recorded location transactionally. Preserve the old copy. A retry after interruption must converge on the same verified destination. If the recorded root is unavailable, outside the supported legacy layout, or the content cannot be verified, report the missing evidence and offer an ordinary pinned refresh. Preserve the prior installed rows, version and recorded path on a failed migration. Never stamp a replacement release or checksum solely to make an old path look current.

An existing committed bundle with a pending marker follows the verified reconciliation path. Preserve unrelated directories, unknown or historical pending bundles and abandoned staging of uncertain ownership. Clean a temporary directory only with positive task ownership and proof it is unreferenced by an active build or committed install. Point an operator to inspection for everything else. Persistence here covers normal restart and disposal of the staging volume. The current backup contract lists selected standalone references and excludes expanded directories from wholesale archives. A restore can require a fresh download. [Backup and restore](../install/backup-restore.md)

## Alternatives and acceptance

Continuing with advisories for all environmental conditions maximizes compatibility on shared mounts. It leaves operators responsible for the writable hierarchy and does not align the setup and worker verdict by itself. Strict refusals everywhere would also block benign platform ancestors and existing provisioned installations. The matrix confines automatic repair to app-designated directories, preserves supported system boundaries and asks for another root where a new write cannot meet the policy. Retaining bundles under the staging override would avoid a cross-volume copy but would make that override persistent for MONDO/HPO and require operators to retain or relocate it indefinitely.

Use small generated public-format files and disposable directories for verification. Run the existing `TestSetStoragePath` cases for the cooperative umask, nested new parents, owned repair, the two foreign-owner modes and the shared ancestor. Inspect both HTTP status/body and the actual modes. For the override case, compare the paths assessed during selection with those used by the initial build and Huey worker. A successful synthetic install must resolve the committed primary path and all three verified files after the staging directory is detached.

| Environment | Required implementation check |
| --- | --- |
| Native Linux and macOS | Exercise default and split roots, owned repairs, foreign-owner simulation and retained reads after a restart. Run the Darwin publication synchronization and platform-boundary checks on macOS. |
| Docker Compose | Exercise the named volume and a separately provisioned bind mount as the non-root application user. Confirm both API and worker see the same persistent bundle and effective override. |
| WSL2 | Exercise a Linux-filesystem data directory. For a Windows-backed mount, assess observed capabilities and provide the Linux-filesystem alternative when requirements cannot be established. Native Windows is outside the supported installation matrix. |
| Existing, interrupted and concurrent installs | Cover complete legacy bundles, missing disposable volumes, mismatched evidence, cross-volume copy failure, pending-marker retry, an already-published identical destination, and a changed installed version. Assert the prior committed row and its evidence survive failed attempts. |

Only the Linux baseline and synthetic fixtures were exercised for this proposal. The platform and migration cases above are acceptance work for the implementation. The decisions sought are the treatment of writable or foreign-controlled locations and the home of retained source evidence.
