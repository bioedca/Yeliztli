# Opening a registered sample database

**Proposed decision for #2462.** A user opening a sample should receive the
database registered to that sample, including after an upgrade or supported
relocation. Use one registry operation that accepts the sample ID for
existing-database access. Reserve creation and publication for the import,
merge and restore operations that explicitly own a new database.

## Compatibility decision

Allow a configured samples directory to be relocated as a unit. Establish its
trusted directory identity at startup and require an explicit configuration
reload or restart when it changes. A per-sample database must be one existing
regular file directly inside that directory, with one registry owner. Support
the normal ingestion basename and the distinct, opaque names generated by the
sample merge service. A basename or numeric suffix is insufficient proof of
sample identity. Use corroborating local metadata where the format provides
it. A contradiction blocks access.

| Existing installation | Proposed behavior and migration |
| --- | --- |
| Standard relative registry entry for an ingested or merged sample | Open the existing file after verifying unique registration and identity. Both issuing workflows keep their own filename conventions. |
| Relative spelling with redundant components, or an absolute legacy spelling that verifies as the same direct child | Permit a one-time normalization to the portable relative spelling after proving directory, file and owner identity. Preserve the file contents. Keep a conditional registry update so a concurrent change cannot be overwritten. |
| Relocated whole samples directory | Support the operator-selected directory as the trust root. Revalidate every affected identity and clear old cache entries when the root changes. A stale absolute path from a former location needs explicit reconciliation. Never select a replacement by matching its basename alone. |
| Individual file is a symbolic link, has multiple hard links, or more than one sample claims one physical file | Withhold affected opens pending explicit repair. Allow moving an operator-verified copy into ordinary storage or restoring from a known backup. Require a unique registration and a fresh identity check before use. |
| Missing row, missing file, wrong file type, outside-root target, or unprovable legacy identity | Leave database and registry intact. Preserve the existing missing-sample/file 404. Use a distinct, stable “sample storage needs repair” conflict for a known but unverifiable registration. Background work records a safe failure category. |

Require a recoverable SQLite snapshot before an operator repairs old storage.
Use a consistent online backup or stop all writers and preserve the database
and its associated journal files together. Verify the restored snapshot and
its sample identity before changing the registration. A copy of the main
database file alone can omit committed changes held in the write-ahead log.
Keep the original files and registration until the checked replacement commits.
Provide a read-only migration preview with counts by disposition. Never auto-copy,
rename, delete or follow an ambiguous file during application startup. An
interrupted registry-only normalization can be retried against the original
row and verified again. A failed migration leaves the previously recorded
value available for repair. Persistence and presentation of diagnostic
categories should also follow [#2710](https://github.com/bioedca/Yeliztli/issues/2710).
Keep full paths, names, sample content and mismatching metadata out of
responses and durable diagnostics.

Allowing per-file links would preserve an existing convenience but require
tracking a second storage location and its ownership across backup, restore,
deletion and cache reuse. Requiring every component of the configured root to
have a particular lexical spelling would instead break whole-directory moves.
An ID-based operation with the compatibility rules above supports ordinary
installs and whole-directory moves while making individual exceptions visible
to the operator. The main migration cost is those per-file layouts. The
potential impact of a mistaken association is disclosure of another sample
or a write to the wrong database. Local data-directory control limits
likelihood under the project's [security policy](https://github.com/bioedca/Yeliztli/blob/main/SECURITY.md).

## Current boundary and rollout

At `cf08f712a130591598eae00648a1b8dce2d0b384`, ingest writes an ID-based
relative path and merge writes a relative path with a publication identifier.
The public baseline contains 26 calls to the shared route resolver plus its
definition in 15 files. A separate textual inventory of direct data-directory
and registry-path joins found 62 lines in 50 backend files. These are search
counts, with overlaps and non-opening uses. Evaluate each usage by its role
when migrating. The [legacy refresh in #2606](https://github.com/bioedca/Yeliztli/pull/2606)
recognizes normalized aliases for its particular repair, requires unique
identity and withholds publication on failure. The shared policy must also
apply to an ordinary current database and cache hit, before any schema,
prompt or recovery write.

| Production consumers | Regression boundary |
| --- | --- |
| Analysis, risk, variant, annotation, QC, browser and batch routes | Use the registered ID. Cover an ordinary and a merged sample, a missing file, and an unverifiable registration. Preserve endpoint-specific freshness and disclosure behavior after a valid open. |
| Dependencies, staleness, worker tasks, update and prompt services | Resolve before background use as well as foreground reads. A failed verification cannot initialize or migrate a database, advance a marker or publish a prompt. |
| Individual and sample summaries, reports, FHIR, queries and exports | Scope each open to its own registered sample. Partial multi-sample responses must follow the endpoint's existing unavailable-data contract and never attribute another sample's result or counts to it. |
| Ingest, merge, delete, backup and restore | Distinguish new staged artifacts from existing registered inputs. Verify owned sources before opening, disposing, copying or deleting them. Revalidate a staged publication before registering it. Keep archive validation, transactional recovery and existing user-visible missing-file behavior. |
| Registry cache, schema setup and legacy repair | Bind locks and cache entries to the verified sample and its current file identity. Invalidate and dispose a superseded engine on replacement, deletion or restore. Failed verification cannot return a cached engine. Preserve the atomic refresh behavior from #2606. |

Verify identity through the operation that opens or mutates the file. A
separate preliminary check cannot certify a later open if the mapping has
changed. The implementation must account for SQLite's auxiliary files,
existing pools and concurrent publication on each supported platform. Where
the storage system cannot establish the required identity, surface the repair
state before content is accessed.

For acceptance, create disposable synthetic databases with opaque sentinel
values and assert both positive and negative results through the production
resolver. Cover standard and merged names, equivalent legacy spellings,
whole-root relocation, each repair category, and a registration change during
open or normalization. Exercise cold and warm caches, a restore/replacement,
fresh and legacy schemas, read and write consumers, and a repeat migration.
Verify the authorized sample's sentinel, absence of unintended data or writes,
and noncreation of missing files. Add a source-level inventory check for new
registered-input opens outside the approved boundary, with explicit audited
exceptions for genuinely new staged databases.

Approval of the per-file link policy, absolute-row migration and repair
behavior is requested before changing existing installations.
