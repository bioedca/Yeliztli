# Upgrading GTEx v8 installations with gene names

Use content readiness to offer an explicit rebuild of a legacy installation. Build a complete replacement privately and publish it through the existing standalone database publisher. Keep the reference release string exactly `v8`. The Health, setup and repair behavior below is proposed for the implementation ticket. [Upgrade feature #2427](https://github.com/bioedca/Yeliztli/issues/2427)

## What existing users see

A legacy installation can still return tissue associations and a top gene ID. Variant Detail reads the name from the installed database on each request. An individual gene without a mapped symbol can continue to use its labelled Ensembl ID.

At revision `4e6788ef`, nine synthetic installs exercised `get_database_health`, `get_database_status` and the Variant Detail badge reader. A missing or empty name table produced a badge with a null symbol, while a table missing the `gene_name` column suppressed the entire badge. All three stamped databases appeared ready and downloaded. An empty association table produced a fourth discrepancy. Health reported corruption while setup still reported the file as downloaded. Two additional synthetic controls reproduced the repair risks. A complete two-tissue install was replaced by a one-tissue archive that passed current publication checks. In a map with one valid symbol and one dot placeholder, the badge reader returned both values verbatim for their respective genes. The setup list and its worker both use the downloaded flag to skip builds. A separate Variant Detail probe returned different top genes and tissues when the same two tied associations were inserted in reverse order.

## Readiness and recovery for #2427

Share a read-only assessment of the installed file and stamp across Health, setup and both build workers. Keep this assessment independent of job activity. Avoid opening a database that is absent. Run blocking SQLite and filesystem work off the API event loop in the async list and download-trigger routes, as Health already does with `asyncio.to_thread`. Use a bounded wait for busy storage. The UI needs the repair eligibility and reason alongside `downloaded`, since several false states require refusal. Inspect the published association table's consumer columns and nonempty content first. For the map, require readable `gene_id` and `gene_name` fields, a primary key or unconditional single-column unique constraint on `gene_id`, and at least one usable symbol whose exact key occurs in the associations. Require usable indexes for both exact consumer lookups on the core table. The legacy `idx_gtex_eqtl_gene` supports the overlap probe, and `idx_gtex_eqtl_rsid` supports Variant Detail. An equivalently usable index qualifies regardless of its name. A tissue-restricted partial index, an expression on the ID or a different comparison collation cannot establish this access path. An entirely unusable or disjoint map may require reading the map to establish that fact. If either lookup lacks an applicable index, report `partial` and offer staged rebuilding. Skip an unindexed gene overlap probe. When the rsID lookup would scan the association table, keep the rows in place and report that the badge lookup is unavailable until repair. Explicit Verify reports the missing access path even when SQLite integrity and name coverage pass. Health polling leaves the working association rows in place.

For each badge, match the full gene ID, including its version when present. Trim the symbol. Use the labelled ID for a missing match, a blank, `.`, `NA`, or the gene's own ID with or without its version. Other exact, usable mappings in a valid map still display. If uniqueness is absent or unverified, withhold names from that map and keep serving the underlying associations. This prevents conflicting names from being selected by row order. For the badge's top association, use the smallest non-null p-value and break exact ties by full gene ID, then tissue, in ascending binary text order. Apply this same rule when reading legacy and rebuilt files. When all p-values are null the top fields stay null. Earlier releases could highlight either tied row. The tie rule only determines which equally ranked association is displayed.

| Build claim held by another worker, including a running Huey update with no linked setup job | `building`, with unknown job ID and progress unless a trusted job mapping exists | Show an active build and disable competing repair and Clean. If there is a published artifact, readers use it during staging. |
| Retry after build or publication failure | Re-evaluate the installed artifact after recovery | Report the job failure and offer another complete staged build. A previously usable install remains available. |

Health gives active work precedence over the idle states. For setup it can resolve the job via `download_session_jobs`. For an external worker it must check the GTEx cross-process build claim in addition to the process-local lock. An unlinked claim identifies activity only. Report `active_job_id=null` and no percentage for that case. Callers that receive a job ID from the manual update trigger can poll `GET /api/updates/job/{job_id}`, including before the Huey worker acquires its claim. The automatic-update status table omits GTEx.

Overlay session and lock activity only for observers. After acquiring the build claim, each worker rechecks the artifact and stamp directly. Calling the aggregate Health calculation there would see the setup worker's own linked pending or running job and return `building` before inspecting the file. The under-claim assessment must yield the actual result even in that case. The cleanup worker excludes its own claim while checking other activity and the underlying removal policy.

When idle, check the recorded release before offering an install for a missing file. A non-v8 stamp takes precedence over absence. Setup and Update Manager must both decline a v8 repair for that combination, even if the user bypasses the UI. A genuinely absent file with no stamp or a v8 stamp remains eligible only after checking the directory entries for orphaned SQLite sidecars and unfinished publication. Inspect without opening SQLite. Recheck under the exclusive publication lease before checkpointing or opening a missing destination. An inconclusive filesystem check always preserves the files.

Both setup's database download worker and the Update Manager's explicit `POST /api/updates/trigger` can rebuild GTEx. The Huey update worker reaches `run_standalone_build` even though the automatic update checker does not offer GTEx. Put one eligibility check under the build claim on both paths, including direct or already queued jobs. Before replacement, recheck the installed release and file identity through the publisher's existing exclusive lease. Use the already held access context for that recheck. If the file changes, access is inconclusive or the stamp names another release, preserve it and return the reason. An ordinary repeated request after successful repair should find a ready v8 install and avoid another rebuild.

Explicit Verify runs SQLite integrity and checks installed name coverage across every distinct associated gene ID, including version. Every ID must have one usable mapping. If a two-gene file names only one, Health can still report ready and the badge can fall back for the other, but Verify reports incomplete coverage and offers repair. This local coverage check needs no upstream download. The verified sources supply the authoritative symbol comparison during candidate validation.

Explicit repair after a failed Verify is a distinct request. Carry that intent to the owning setup or Huey worker. When the fast assessment says ready, that worker rechecks the same installed artifact with the deep validator under the build claim before deciding to skip. A fresh confirmed integrity or name-coverage failure permits staged repair. A clean result on a now-healthy file is a no-op. Transient access errors remain unverified. Bind the decision to the observed artifact identity and check it again at publication. The caller's request and a previous failure alone cannot authorize replacement. Health polling and ordinary duplicate requests still use the fast check.

The repair action for a usable database must submit the optional GTEx build directly. System Health currently derives `can_clean` from `partial`, and the clean endpoint checks the state again independently. Suppress Clean for usable legacy data in the UI **and** refuse its removal in the endpoint under the build claim. Verify should explain which component needs repair. Opening Health or visiting a sample must never start a multi-gigabyte transfer.

Prove input completeness before accepting a **candidate**. The reviewed v8 evidence records the full tar's SHA-256 as `c61ac336daf86a92f1596ee59de7dd5e60d451a507a6d7a15d8b030a0266ac5d` and identifies 49 tissue files of each kind. Pin this digest and a separately verified SHA-256 for the matching rsID lookup in the build manifest. Verify the actual bytes for cached and freshly downloaded inputs before extraction. The existing pipeline pin supplies a URL and release label. A checksum calculated only from the download under test supplies no independent expectation. [GTEx v8 artifact evidence](https://github.com/bioedca/Yeliztli/tree/4e6788efa6c5a7e888a09cd3ee8aec3c4bf141ea/data/science-evidence/2026-10-13-gtex-v8-egenes-gene-names-2087)

Use the verified archive's member inventory to check that the expected pair and name files for each tissue were extracted and consumed. Refuse a missing member, duplicate tissue input or unexpectedly skipped tissue, even when other tissues produced valid rows. Deep validation of the staged candidate must check every distinct versioned gene ID in its association rows against the verified v8 egenes inputs. Require exactly one usable matching source symbol per ID. The existing v8 evidence found a name for every gene in the significant-pairs files. A single overlap suffices only for fast installed-file polling. Reject a candidate with a missing, conflicting, placeholder or incorrect symbol even if other genes are named.

For every readable usable core eligible for v8 repair, including one whose stamp is missing, a display-only upgrade must preserve the association values and multiplicity. Compare a canonical digest of those logical records on both sides, excluding SQLite row IDs and physical order. Include rsID, versioned gene ID, tissue, coordinates, p-value and slope. Perform the expensive comparison during the explicit rebuild. If the result differs, keep the working file and report an association-data change. For a first install, an absent file with a leftover stamp, or a confirmed damaged core, there is no usable set of old rows to compare. Derive the expected per-tissue logical records independently from the verified significant-pairs inputs joined to the pinned rsID lookup. Apply the documented row eligibility and missing-rsID filters, preserve multiplicity, and compare the complete records with the candidate using the same canonical digest. The validator must not reuse the loader's emitted rows or its reported counts. An omitted eligible pair fails validation even if its tissue and gene still occur elsewhere. Run the installed-file readiness assessment against the **private candidate path and staged version row**. Require `ready` with the exact v8 stamp, expected association indexes, a usable exact overlap and unconditional name-key uniqueness. Deep source and content checks and SQLite integrity are additional publication requirements. A missing index or uniqueness constraint must stop publication even when every value matches. On ordinary failure before the version commit, preserve the previous file and stamp. A process death around rename or commit requires the publisher's existing digest-bound journal and startup recovery. Readers must wait at the publication boundary. The GTEx staging database is transient, so retry can repeat the full ingest. [Standalone publication and recovery](../install/reference-data.md#rebuilding-standalone-databases)

## Costs and alternatives

| Option | Inputs, resources and compatibility |
| --- | --- |
| Content readiness and private rebuild | Reuse the existing publisher for every supported legacy layout. Budget for the installed database plus a replacement, extracted inputs and downloads. The loader estimates about 1.6 GB for the tar and 0.8 GB for the lookup. The issue reports a 9.6 GB installation, while the registry's 3 GB figure is an estimate. Use actual free space and installed file size when presenting costs. A missing source or failed download leaves the old file usable. |
| Transactional name-only backfill | With complete release-matched egenes inputs this could avoid reloading all tissue pairs and a second full database. The existing loader parses names before replacing rows, but schema creation is separate and the loader accepts a nonempty subset of files. A supported live backfill would also need input completeness and identity checks, a writer claim, a transaction covering schema and rows, safe readers, and interruption and retry coverage. Absent, incomplete or unverified inputs require another path. |
| Separate source and loader versions across the application | An independent schema-capability field could serve future sources. Extending the public snapshot and migrating historical samples costs more than inspecting this one optional artifact. A global suffix rule could suppress meaningful changes for other databases. Keep exact per-source comparisons. |

Memory also limits a full rebuild. The loader holds the release-wide variant-to-rsID dictionary and one tissue's parsed rows at the same time. Setup runs the builder in an API-process thread. Measure peak resident memory and temporary disk use on a complete verified v8 build before quoting system requirements or enabling repair. The 9.6 GB file size describes disk use and supplies no RAM estimate. Give low-memory installations an explicit choice to defer and keep using their current associations. Name-only backfill would need memory for the name dictionary and space for its transaction journal. It avoids allocating the full variant lookup and tissue row lists.

The selected path uses the full v8 build whether extracted egenes files survive or are absent. Create a private directory for each build under the configured downloads root. Put the tar, lookup, partial transfers and extracted members there, and verify and consume those same files. Different installations can share a downloads root while holding independent build claims. Record an opaque build ID and its private directory in the owning installation before download. Bind the local recovery record to the directory identity and a matching ownership marker. Hold an exclusive per-directory activity lock throughout use. On normal completion or failure, reclaim this build's inputs while holding that lock, then release it. After a crash, recovery in the same installation can reclaim the recorded directory only after acquiring both the installation build claim and the same directory lock and rechecking its identity and marker. If ownership or liveness cannot be established, preserve it and show the operator the recorded build for investigation. Never sweep the shared downloads root by age or filename. The downloader can resume its own partial transfer within that build. A later build starts fresh. Leftover extractions or completed downloads have no role in this upgrade without verified provenance and exclusive ownership. With insufficient space, unavailable sources or an incomplete release, show a retryable error and preserve the old artifact.

## Acceptance

The synthetic upgrade test runs the existing standalone builder with a local fixture archive in place of the network download. It seeds fixed historical rsIDs, versioned gene IDs, tissue, positions, p-values and slopes independently of the rebuild loader in a pre-name-table v8 file. The same retained reader sees both original association records and the added names after publication. The Huey worker leaves a recorded v8 sample current with no prompt. For an unstamped working install and a valid snapshot that omits GTEx, both workers establish v8 provenance. Huey immediately creates one normal version-staleness prompt. Setup completes the build without running that precheck, so the same difference is visible to the next ordinary precheck. The test inspects persisted prompts before and after each worker. Setup currently skips stamped legacy files at admission. For #2427, exercise the repaired admission through the setup worker on that fourth case and require published names and no new prompt. Both paths preserve the original snapshot. A deliberately distinct release still produces the expected staleness record. Existing publisher tests also cover interruption before and after the version commit.
