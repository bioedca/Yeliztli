# Offline VEP annotations

**Proposed decision for #2299.** Distribute a single verified VEP reference pack that users can transfer to a disconnected installation. Let setup import it locally. Retire the old fixture when the offline import and existing-install recovery both work. Until a pack is verified, mark VEP unavailable and withhold its consequences. This decision covers provisioning VEP on a machine where the other required reference databases are ready or have a separately supported offline provisioning path. An empty installation also needs its required setup data before the wizard will expose variant detail. The open product choice is whether a fresh installation must supply verified annotations **without** that extra transfer.

## What users receive today

| Path | Observed behavior on the historical revision |
| --- | --- |
| Source checkout or editable install with the committed file | Reading database status can copy `bundles/vep_bundle.db` into an empty data directory. Status reports downloaded and leaves the version row empty. Explicit fallback installation then records `v1.0.0`. |
| Built Python wheel | The inspected `yeliztli-0.2.0-py3-none-any.whl` contains zero members named `vep_bundle.db`. The wheel alone cannot supply that file to a disconnected first install. The Dockerfile also lacks a copy of the top-level bundle directory. The image observation is from source inspection. |
| Normal setup wizard | The wizard lists databases, which can materialize the historical fixture in a source checkout even with working internet. VEP is an optional bundled database. The wizard excludes it from selectable downloads. Continue depends on the health of the separately required databases, including ClinVar and dbNSFP. An AncestryDNA upload blocked on the VEP version offers a separate update action. |
| Explicit VEP database download | The worker acquires the bundle claim and tries the remote runner. If status already copied the file with no version row, a failed first remote attempt can still complete by recording the legacy version. With an existing stamp and a readable manifest that identifies a newer version, a failed asset fetch leaves the outdated file and the job reports failure. Without a readable manifest, any recorded version suppresses this job. A VEP-only database download request can return HTTP 409, “already downloaded,” even for the legacy stamp. |
| Successful download | The updater replaces the working file, attempts to mirror it into a writable source tree, then records the version and update history. It checks SHA-256 when the manifest supplies one. Embedded-version disagreement currently produces a warning. A mirror in a previously updated checkout can therefore differ from the bytes in Git. |
| Backup restore | Backups can include optional standalone reference databases. Setup compares archived sample-version metadata against the installed version, and an accepted backup can publish an archived VEP SQLite file over the installed file. A sample-version check alone cannot authenticate those replacement bytes. |
| Annotation and display | The annotator resolves rows by allele and position and saves primary consequence and HGVS fields per sample. Variant detail returns stored fields and also reads transcripts from the installed bundle. The page and side panel render these fields. Existing samples can carry an older stored primary value after the file changes. |

The historical source fixture is **11,374,592 bytes**. All **102,254** rows are single-base pairs with REF alphabetically before ALT. Only 2,742 rows have a protein HGVS field. Ordering alone cannot identify which rows are wrong. Two synthetic controls went through the production annotation worker with only the legacy fallback. Both jobs completed and stamped the samples `v1.0.0`. For the heterozygous control, variant detail returned `p.Arg27His` in its primary field and transcript list. Chromium displayed it on the Overview and Protein tabs. GRCh37 Ensembl maps the same T>C genomic change on `ENST00000311124.4` to `c.80A>G` and `ENSP00000308895.4:p.His27Arg`. The fixture omits the transcript version. Its genomic REF is reversed and its output disagrees with the public versioned transcript currently associated with that identifier. The absent-variant control returned HTTP 404. [Public transcript query and reproduction](https://github.com/bioedca/Yeliztli/tree/main/data/science-evidence/2026-11-19-vep-offline-fallback-2715)

The second control carried two copies of the GRCh37 reference base T. The worker classified it as `hom_alt` with REF C and ALT T. The carried-only VCF export included it with `GT=1/1`. This reaches both the definition of which variants are exported and their allele identity. A repair must address genotype interpretation and stored annotations in addition to the protein label. [Synthetic worker and export records](https://github.com/bioedca/Yeliztli/blob/main/data/science-evidence/2026-11-19-vep-offline-fallback-2715/raw/fallback-baseline.json)

The legacy resolver prefers a registry stamp, then an embedded version, then `v1.0.0`. AncestryDNA ingestion blocks malformed versions and versions below `v2.0.0`. The 23andMe path lacks that gate. Sample freshness uses the bundle major version. Replacing bytes, including with a corrected artifact of the same major version, can leave already-stored annotations readable. A release checksum establishes which file arrived. It cannot adjudicate its allele directions. [Bundle build and release](../bundle-release-runbook.md)

## Three support contracts

| Choice | Disconnected first install | Cost and consequence |
| --- | --- | --- |
| Ship a verified full rebuild | A source, wheel or container installation receives verified calls across the declared catalog. A like-for-like rebuild targets the 102,254 legacy sites. A wider contract targets the full vendor union. | The v4 release matches both rsID and position for 101,958 legacy sites. Projecting those release rows with two indexes occupied 19,357,696 bytes. The complete union release is 352,251,904 bytes. Allow staging space. Resolve the 296 missing sites and verify all retained rows before promising full legacy coverage. |
| Ship a verified subset | Only named sites, alleles, transcripts and verified fields have offline coverage. Publish a machine-readable inclusion list with its denominator, release and omissions. Return an explicit unavailable reason outside it. | Smallest option that can supply annotations immediately. Requires the API and UI to distinguish absence, an unreportable allele, a verified hit and a sample with no alternate allele. A partial pack must never qualify for a full vendor catalog by version alone. |
| Retire the fixture and support local import **(recommended)** | Without a pack, setup shows VEP unavailable and offers a local import. With a prepositioned pack, validate and install entirely offline. Package and online installs use the same verifier. | Keeps a single reference release and avoids charging every wheel download for a large artifact. Adds one transfer for disconnected users. Removing the file before delivering import and recovery would strand them. |

The like-for-like measurement used both published digests. Among the other 296 sites, one legacy identifier occurs elsewhere and 295 identifiers are absent. Ten of the 296 have a matching coordinate and unordered allele pair under another identifier. Keep them as candidates for independent alias reconciliation. The size estimate counts only exact identifier-and-position matches. The 101,958 matched sites had 169,315 release rows across alleles. Every matched site had its historical unordered allele pair among those rows. The 19.4 MB figure measures the annotation table and its two indexes in memory. Distribution metadata, verification data and the unresolved sites would affect the final size. A transfer-only pack can use the same catalog definition. [Reproduce the projection](https://github.com/bioedca/Yeliztli/blob/main/data/science-evidence/2026-11-19-vep-offline-fallback-2715/probe_release_projection.py)

For the recommended option, the application needs a trusted release manifest available offline, bound to the application or authenticated independently of the transported pack. Validate artifact type, compatible app/schema, build, release, byte size, digest, coverage scope and the release's verification receipt before publishing. A freely editable checksum next to a replacement cannot establish its identity. Keep the installed digest and coverage identity with annotation state. Deduplicate repeated imports by those identities.

## Where the input can go wrong

The default `scripts/generate_vep_input.py` path uses a parsed vendor call. The 23andMe parser sorts the two bases, and the generator takes the first as REF. In a synthetic site with known REF G, both orders of a heterozygous call yielded REF A and ALT G. A homozygous G produced REF G and no ALT. The separate catalog-VCF mode emits N and a missing ALT. The rsID list supplies identifiers alone. None of those outputs establishes reference orientation. The documented v4 build instead uses matching release-112 variation features as VEP coordinate input. The legacy Git blob first appeared in the initial commit. This demonstration identifies a reproducible failure mode without attributing the blob to an undocumented command.

## How to build and verify a candidate

1. **Pin the inputs.** Use the release-documented union catalog as a site list only after recording its origin, permitted reuse, hash and denominator. Map each site to a primary GRCh37 chromosome accession with an explicit coordinate convention. The release-112 Ensembl variation-feature dump, region mapping, primary-assembly FASTA and offline VEP cache have identifiable sources. Record their byte-level checksums, package/tool versions and commands at build time. Exclude ambiguous placements, unsupported representations and third-party data lacking redistribution clearance, with counts by reason. [Input records, terms and provenance](https://github.com/bioedca/Yeliztli/tree/main/data/science-evidence/2026-11-19-vep-offline-fallback-2715)
2. **Derive REF from the assembly.** Look up the complete reference span on the forward strand for each normalized allele. Carry the source placement, strand and original coordinates through normalization. Spell out one-based VCF and zero-based source offsets where applicable. Enumerate ALT alleles separately. Reject mismatching REF, ambiguous indels, aliases that cannot be resolved to one placement, or an allele-specific consequence without a unique ALT mapping. Retain counts and reasons. Alphabetical, minor-allele and assay order cannot determine the reference.
3. **Keep consequence identity.** Retain assembly, contig accession, coordinate, REF, ALT, transcript accession **and version**, strand, protein and their source versions. Record the projection and preferred-transcript rule. Reconcile multiple placements and transcripts before projecting to the runtime schema. The existing VCF builder selects by `(rsid, alt)`, can keep only the first ALT for an unannotated multiallelic site and accepts CSQ text without reference verification. Its seed-CSV path accepts caller-supplied fields. Prevent development fixtures from entering a production release. Six CLI probes demonstrate that both entry points store the correct synthetic input and also store reversed genomic inputs and independently reversed coding strings presented to them. [Builder probes](https://github.com/bioedca/Yeliztli/blob/main/data/science-evidence/2026-11-19-vep-offline-fallback-2715/probe_builder.py)
4. **Verify after SQLite serialization, independently of the producer.** Start from the declared input catalog and disposition table, enumerate every expected normalized allele, compare full identity, cardinality and field availability in both directions. Fetch the indicated reference span independently, for example from the paired NCBI assembly using an accession map and an implementation that does not import the builder. For reportable coding/protein names independently project the allele through the pinned versioned transcript alignment, replay it on the transcript/CDS and translate using the applicable published translation table. Compare **both** reference and alternate residues, positions and strand. Handle synonymous, noncoding, splice and complex cases within the verifier's declared capabilities. Withhold unverified fields or exclude the row under the published scope. Withhold a release for unexplained discrepancies, duplicate identities, unmapped or unaccounted rows. Ensembl and NCBI share the GRC reference, and transcript resources can share submissions. Independent software checks a transformation against that reference. Clinical effect claims need their own independent evidence. [McLaren et al., 2016](https://doi.org/10.1186/s13059-016-0974-4)
5. **Publish an auditable receipt.** Include input and output hashes, build-specific versions, inclusion/exclusion counts, the complete decision on allowed missing fields, deterministic ordering and reproducibility results. Require the verifier to fail deliberate genomic reversal, wrong strand/build/transcript version, protein-only reversal, dropped ALT, unexpected duplicates and a stale copy under a current stamp. Include correct REF alphabetically after ALT, a minus-strand transcript, multiallelic and absent-site controls. Establish the expected results outside the parser and runner. The downloaded v4 asset matched its pinned digest and metadata. Its matching-site count and one verified sentinel leave artifact-wide scientific verification outstanding. Report the fraction of single-base rows with REF alphabetically before ALT. The parent issue’s proposed 90% alarm would catch this legacy file. A distribution screen can miss individual errors or flag a biased subset, so release acceptance requires the row-level oracle. [Current bundle release](https://github.com/bioedca/Yeliztli/releases/tag/bundle-v4.0.0)

## Upgrade and acceptance gates for #2299

| Starting state | Required result and evidence |
| --- | --- |
| Empty or disconnected install | Exercise setup and status in clean source, installed wheel and built container, with networking disabled. Start once without other required references and assert their setup gate. Then pre-provision those references, leave VEP absent and test the import and variant page. Supply the missing required references separately if a whole-application disconnected first install is promised. Include a source checkout whose bundled copy was previously replaced, and isolate fixture consumers from runtime install sources. Check availability before import and after a verified import, and check the persisted version, digest, coverage and a real response body. A status read must never revive the retired digest. |
| Known legacy digest, including a mismatched registry stamp | Prevent new results from using those bytes. Preserve user input, identify affected or unverifiable prior annotations, withhold the affected fields and offer reannotation. An interrupted upgrade must reopen in a truthful recoverable state. |
| Unknown file, stale stamp, restored sample or no source identity | Exercise a missing manifest and a separately unreachable asset with a readable manifest. Detect actual content before trusting a version. Expose unverified availability and a recovery action. Test backups containing only sample annotations, as well as ones with older metadata. Avoid attributing stored fields to a newly installed release. |
| Restore includes `vep_bundle.db` | Exercise the normal backup import over a verified installation with a legitimate older backup containing the legacy file. Include matching sample major versions and a reference-only archive. Validate every archived VEP file before publication. On rejection retain the installed pack, its identity and the existing sample state. An accepted restore must bind each restored sample to its actual annotation source and trigger recovery when that identity is absent or differs. |
| Verified full or partial pack already installed | A failed download, digest mismatch, truncated copy or incompatible schema preserves the usable pack and its identity. A partial pack cannot silently replace full coverage. Re-importing the same verified release is idempotent. Test the running process with a warm database connection during an atomic replacement. |
| Samples annotated before replacement | Detect changes in verified content and scope, including within the same major version. Recompute or withhold stored primary HGVS and reconcile it with live transcripts, recompute or withhold genomic REF/ALT and zygosity, and refresh list/export and downstream VEP-derived fields before reporting the sample as current. Preserve independently sourced annotations. Coordinate stored findings with #2705. |
| Prove the repair | Exercise the public sentinel through installation, annotation, detail API and rendered variant page. Compare expected genomic and transcript identities with independent evidence. Add synthetic carried, hom-ref non-carrier, absent, reverse-strand and ambiguous cases, both supported vendor paths, cold/warm reads and annotation after retry. Assert exact VCF REF/ALT/GT for a reportable reference call and that the carried-only export omits the reference homozygote. Record release coverage by allele and by reportable field. |

The design decision can be reviewed now. Enabling release use in #2299 requires a verified artifact, a supported disconnected workflow and recovery of existing installations under the chosen contract.
